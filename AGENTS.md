# AGENTS.md

Instructions for AI coding agents (Codex and others) working in this repo. Claude Code reads `CLAUDE.md` instead; both files describe the same rules. `CLAUDE.md` has the full test layout and gotchas, and wins if the two ever disagree.

Ethereum token launch: an ERC-20 sold by a 20-minute stepped Dutch auction with uniform clearing. Solidity 0.8.24, Hardhat, OpenZeppelin 5.0.2, React and Vite front end.

## Source of truth
- `SPEC.md` is the approved spec. Change behaviour only after the spec changes. Spec changes go through the `spec-amendments` branch, in their own PR.
- `PLAN.md` lists milestones and the risk register. Each risk names its covering test.
- Read `CLAUDE.md` before changing code: its Layout section says which test file covers each acceptance criterion (AC1 onwards).

## Commands
- `npm ci`: install. Never `npm install`; on Windows it rewrites `package-lock.json`.
- `npm test`: contract tests.
- `npm run frontend:test`: front-end tests (Vitest).
- `npm run frontend:build`: front-end build.
- `npm run frontend:build:check`: front-end build against a fixture deployment, then a check that the bundle keeps App's render paths.
- CI (`.github/workflows/ci.yml`) runs all four, plus Slither on the contracts, and is the merge gate. Run them yourself before saying a change is done, and report the real results.

## Rules
- Never push to `main`. Work on a branch and open a PR.
- Every behaviour change needs a test. Name new tests after their acceptance criterion (`it("AC61: ...")`, `SlowPollAC61.test.jsx`). A new test must fail without the fix; check by reverting the fix once.
- Don't edit `frontend/src/deployment.json` (generated by `scripts/deploy.js`), `SPEC.md` (outside `spec-amendments`), `.claude/settings.json` or `contracts/` unless the task asks for it. `contracts/test/` is test-only; never deploy it.
- When you add a criterion's tests, update the `CLAUDE.md` Layout line for it and add a `PLAN.md` risk-register row naming the test.
- Prices are wei per whole token. Token amounts are token-wei (18 decimals).
- Keep diffs minimal and match the surrounding style. Check `package-lock.json` hasn't changed unless you added a dependency.
- Commits made with Claude Code end with the `Co-Authored-By` and `Claude-Session` trailers. With another tool, say in the commit message or PR description which tool helped.

## Review checklist
Use this when asked to review a branch or PR. Don't edit the branch under review; return APPROVE or REQUEST_CHANGES with numbered findings, each marked blocking or non-blocking.

1. **Spec conformance.** Split the relevant SPEC.md text and acceptance criteria into clauses. For each: where is it implemented, and which test proves it? Flag anything missing, and anything the spec doesn't ask for.
2. **Tests prove the change.** Revert only the non-test part of the fix (in a separate worktree or copy) and confirm each new test fails. A test that passes without the fix is blocking.
3. **No regressions.** Run `npm test`, `npm run frontend:test` and `npm run frontend:build` yourself. Existing tests changed only to make them pass need a reason.
4. **Correctness beyond the tests.** Race conditions, state stuck after an error (missing `finally`), timers or listeners not cleaned up on unmount or account change, stale responses that can still update the UI.
5. **Conventions.** Everything under Rules above.

Blocking: a spec clause missing or wrong, a test that doesn't prove its clause, a failing command, a regression, or a broken rule. Everything else (naming, clarity, small simplifications) is non-blocking.

Claude Code users have the same process as two subagents, `.claude/agents/editor.md` and `.claude/agents/reviewer.md`.
